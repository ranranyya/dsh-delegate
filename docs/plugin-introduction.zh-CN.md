# DSH Delegate 插件介绍

**DSH Delegate** 是为 DeepSeek Harness（DSH）设计的本机任务委派插件。它让 Codex 等 MCP 宿主在你明确授权后，把实现任务交给 DSH 当前已经配置好的模型执行；执行结果再返回宿主，由宿主检查改动、验证证据并决定是否验收。

它的分工很直接：**宿主负责理解、规划和最终审查，DSH 负责按配置执行被明确委派的任务。** 插件不会因为对话里提到 DSH 或 DeepSeek 就自动派工，也不会擅自切换到另一个 API 或模型。

## 它解决什么问题

使用多个 AI 工具时，任务容易散落在不同聊天窗口里，API 配置也可能重复维护。DSH Delegate 将执行入口收敛到 DSH：插件复用 DSH 已注册的 API、模型和凭据，宿主则通过一组本机 MCP 工具创建和跟踪任务。

这样你可以继续在 Codex 中讨论和规划，在需要外部执行时明确选择或指派 `dsh-delegate`，再由宿主检查执行结果。授权、执行模型和可选审查都由 DSH 插件设置控制。

## 主要功能

### 一个本机授权开关

- 新安装时默认关闭。
- 开启后，已连接的本机 MCP 宿主可以提交委派任务。
- 关闭后，插件拒绝新任务，并向运行中的任务发送取消请求。
- 查询状态、查看已有任务结果和取消任务不受开关关闭影响。
- 安装或更新 Codex 集成不会自动打开这个开关。

该开关表达的是“是否允许本机提交任务”，不是按用户或进程身份区分访问者的安全隔离。启用期间，同一台电脑上能够访问本机 DSH 端口的进程也可能提交任务，因此只应在你需要使用委派时开启。

### 复用 DSH 中已有的 API 和模型

API 提供方列表来自 DSH 注册的原生 provider，模型和支持的推理强度来自 DSH 的模型元数据。用户不必在插件里重新填写接口地址或 API 密钥。

执行设置可以选择 worker provider、模型和推理强度，并设置超时、最大并发及工作区隔离方式。插件按选定配置执行；如果提供方或模型不可用、配置不匹配，任务会明确失败，不会偷偷改用 Harness 默认模型或其他 API。

### 可单独开启的只读审查

“附加审查”是可选开关，默认关闭。开启后，插件会使用单独配置的 provider、模型和推理强度启动一个独立审查者。审查者只读工作区并返回审查结论，不会自行改代码、自我批准，也不会启动自动修复循环。

这项审查是执行流程中的额外意见，最终验收仍由宿主负责。关闭它不会关闭本机授权，也不会改变 worker 的模型选择。

### 派工前检查和工作区隔离

`delegate_preflight` 会在派工前只读检查指定目录：它是否为 Git 仓库根、是否有提交、是否存在未提交改动，并建议隔离方式。预检不会创建文件、提交、stash、分支、worktree 或任务。

- 干净且已有提交的仓库可以使用 worktree 隔离，让任务从独立工作树开始。
- 有未提交改动时，插件不会自动把 worktree 降级为共享执行。宿主需要根据变更路径判断是否可安全地原地执行，并在明确选择共享后再次预检。
- 非 Git 仓库、没有提交、不是仓库根或无法检查的路径会被阻止，插件不会静默绕过。

任务结果会记录实际隔离方式、基线和可见的变更摘要，便于宿主把执行者带来的变化与原有改动区分开。

### DSH 工作区与对话管理

插件会把任务放进与执行目录对应的 DSH Workspace。对话是**按任务**决定的，不再是目录级的设置：

- **每次新的提交都新开一条会话**。同一执行目录继续使用同一个 Workspace，但每次提交都是一个新
  Session——即使这个目录此前跑过很多任务，即使旧设置文档里还留着已废弃的
  `conversation.mode: "reuse"`。
- **只有显式跟进才续接**：`delegate_submit` 带可选字段 `continueFromTaskId`，指向要继续的那个
  先前任务时，本次任务续接**那一条**会话（同 Workspace、同 Session）。无关任务不要带这个字段。
- 续接是失败即拒绝：未知/已清理的父任务、仍在运行的父任务、没有产生对话的失败任务、换了目录或
  源仓库、已删除的工作树、已不存在的 Session 都会被拒绝，不会悄悄改成新开会话。
- 隔离工作树的跟进任务必须在**同一棵**工作树里继续，因为上一次未提交的改动就在那棵树里。
- 目录级「复用上一对话」开关已移除；设置页不再提供该控件，`setConversation` 会以
  `CONVERSATION_MODE_REMOVED` 拒绝写入。

详见 `docs/conversation-placement.md`。

### MCP 任务工具和记录

插件为本机 MCP 宿主提供五个操作：

| 工具 | 用途 |
| --- | --- |
| `delegate_status` | 查看本机委派开关是否开启 |
| `delegate_preflight` | 只读检查工作区并返回隔离建议 |
| `delegate_submit` | 提交任务给 DSH 执行（可选 `continueFromTaskId` 表示跟进某个先前任务） |
| `delegate_result` | 查看或轮询已提交任务的状态、结果与证据 |
| `delegate_cancel` | 请求停止一个正在运行的任务 |

任务记录会显示状态、实际使用的 provider/model/effort、变更文件摘要、diff、验证证据及审查结果；任务详情也可包含提交的任务说明，方便宿主核对执行范围。API 凭据和连接令牌不会作为普通任务结果提供给宿主。

## Codex 集成

插件设置页提供 Codex 集成操作。点击安装/更新后，插件可以在 Codex 配置目录中安装 `dsh-delegate` 自定义 agent 文件，并登记该插件的本机 stdio MCP 服务。Codex 重新载入配置后，agent 才能使用这些 MCP 工具。

安装与授权是两个独立步骤：安装 agent 不会开启本机委派开关。首次安装 Codex agent 和 MCP 配置仍需从设置页明确点击；插件更新时，只会自动刷新与已知发布模板逐字节一致的旧 agent 文件，不会创建缺失文件、改写 Codex 的 `config.toml`，也不会覆盖被用户编辑或来源不明的文件。

**输入框是否支持键入 `@dsh-delegate` 选中 agent，取决于所用 Codex 版本和界面。** 插件提供 agent 文件和 MCP 连接，不保证每个 Codex Desktop 或 CLI 版本都有 `@` 选择器。若界面不支持，可以通过 Codex 提供的 agent 选择方式显式指派它。

agent 内置了派工规则：只有明确选择该 agent 或明确要求把实现任务交给 DSH 才会提交；普通解释、规划、审查、状态询问以及仅仅提到 DSH 的内容由宿主直接回答。它会先检查开关和工作区事实，再派工并跟踪同一个任务；不会自行打开开关、改用其他执行通道或宣称宿主验收已通过。

## 一次典型使用流程

1. 通过 DSH Desktop 的 Plugins manager 安装或更新插件，并确认插件已启用。
2. 在 `Plugins → Installed plugins → dsh-delegate` 中选择 DSH 已配置的 provider、模型、推理强度和执行设置。
3. 如需额外只读审查，单独开启并选择 reviewer 的 provider、模型和强度。
4. 在需要使用本机委派时开启授权开关。
5. 在 Codex 中明确选择 `dsh-delegate`，并给出实现目标、工作区和验收标准。
6. 宿主检查预检结果与隔离方式，提交任务并轮询同一个任务直到完成、失败或取消。
7. 宿主查看实际模型路由、diff 和验证证据；必要时要求执行者修正，最终由宿主作出验收决定。
8. 不需要委派时关闭授权开关。

## 安全与行为边界

- API 地址、密钥和凭据仍由 DSH 管理；插件复用 provider，不把密钥复制进插件设置或任务结果。
- 关闭开关会阻止新任务，但不等同于关闭整个 DSH，也不隔离本机其他进程。
- 配置的模型或 provider 不可用时任务会失败，不会静默回退。
- 脏仓库不会自动改为共享执行；宿主必须先审查预检事实并明确决定。
- Codex 安装逻辑不会覆盖用户改过的 agent 文件或无托管标记的同名 MCP 配置。
- DSH worker 的“完成”或附加审查的结论都不等于宿主验收；宿主仍要检查实际改动和验证证据。
- `@dsh-delegate` 的可用性由 Codex 界面决定，插件不会自行添加或保证输入框的提及选择器。

## 版本与发布状态

当前开发版本为 **0.1.10**。项目支持声明适用于 DSH `0.2.0-rc.2`、`0.2.1-rc.2` 和 `0.2.1-rc.3`，运行兼容性仍应以目标 DSH 版本上的实际验证为准；运行环境要求 Node.js 24 或更高版本。

目前插件尚未发布到 GitHub 或 npm，也没有官方公开下载地址。本文档介绍的是开发仓库当前源码行为；本地生成的 `.tgz` 属于自建安装包。
