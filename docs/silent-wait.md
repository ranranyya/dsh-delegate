# 静默等待与集中审查（Silent waiting and concentrated host review）

本页说明 DSH Delegate `1.1.0` 引入、并由 `1.2.0` 修正的行为：一个正常推进的任务**不再**让
派工方（Codex）一遍遍醒来读结果；只有当出现真正需要判断的事情时，派工方才被打扰。

`1.2.0` 的修正集中在三处，读本页时请一并参照：等待被中断不等于执行被中断（第 4.1 节）、
串行宿主下的独立控制通道（第 4.2 节）、已安装 Codex 集成的自动升级（第 8 节）。

这不是"让 Codex 不花 token"的承诺。插件无法控制 Codex 自己的上下文、思考或工具调用
开销，也不做省 token 的估算。这里只描述**任务状态的报告方式**改变了什么。

---

## 1. 默认间隔

| 设置 | 默认 | 范围 | 含义 |
| --- | --- | --- | --- |
| `monitoring.selfCheckSeconds` | 300 秒（5 分钟） | 30–3600 秒，整数 | 任务完全安静这么久之后，插件在本机做**一次**只读自检 |
| `monitoring.attentionSeconds` | 600 秒（10 分钟） | 31–7200 秒，整数，且必须大于自检间隔 | 仍然安静这么久之后，才把这件事报告给派工方 |

保存在设置文档里的单位是**整秒**。设置页用"分钟"呈现，二者是同一个值
（5 分钟 = 300 秒）。一个不是整分钟的值（例如 90 秒）在页面上显示为 1.5 分钟，
不会被悄悄圆成别的设置。

这两个值都只能全局设置：项目覆盖和单任务覆盖都**不能**改动它们。

## 2. 核心规则：安静 ≠ 失败

- 任务安静、某个测试跑得久、某个工具调用耗时很长，**都不会**让插件判定失败、
  取消任务或重启任务。
- 真正推进（模型输出、推理、工具调用、工具结果）会**重置**静默计时，属于内部事实，
  不会叫醒派工方。
- 只有"确实没有进展"**并且**超过提醒间隔之后，才会报告 `attention`。
- 提醒只是提问，不是判决。派工方默认应当继续等待同一个任务，除非有**具体**的错误。

连接心跳、结果轮询、页面刷新这类噪声**不会**重置静默计时；否则一个真的卡住的执行器
会永远看起来"很活跃"。

## 3. 5 分钟自检做了什么、没做什么

达到 `selfCheckSeconds` 时，插件对**自己已经持有的**任务记录做一次只读检查：

- 任务是否还活着、执行器是否已经结束；
- 当前阶段；
- 是否有一次工具调用在等待授权决定；
- 当前正在运行哪个工具、已经运行多久。

它**不会**：

- 调用任何大模型（不消耗 token）；
- 读取或分析整个代码差异、也不会读工作区文件内容；
- 改变任务状态、延长或缩短任务的时限；
- 重启、取消或重新提交任务。

自检的结论会显示在任务详情里（"无进展诊断"），例如"执行器健在，这段时间没有新输出"、
"某个工具调用仍在运行"、"正在等待本次调用授权决定"。

## 4. 一次等待只返回一个结论

派工方通过 `delegate_wait` 等待同一个任务。一次调用的默认截止是 **3600 秒（60 分钟）**，
内部由若干次**各自不超过 25 秒**的有界观察组成（执行面自己的上限也是 25 秒）；正常的
任务在内部大约每 25 秒完成一次观察，安静的 20 分钟就是 48 次观察、47 次心跳，而派工方
**只收到 1 个答案**。答案里是一个原因：

| 原因 | 含义 | 派工方该做什么 |
| --- | --- | --- |
| `heartbeat` | 没什么要报告的（内部心跳） | 正常情况下看不到；看到了就继续等待同一任务 |
| `attention` | 超过提醒间隔没有进展 | 读诊断，**默认继续等待**；不要在只是安静时取消或判失败 |
| `permission` | 有一次工具调用在等授权决定 | 审查这一次调用的完整操作，然后决定一次，再继续等待同一任务 |
| `ready` | 执行结束，等待宿主审查 | 读**一次**完整证据，自己审查；这不等于已接受 |
| `failed` / `cancelled` | 运行没有产出 | 读一次记录的原因后报告 |
| `interrupted` | **任务记录本身**已中断（例如进程重启留下），不会继续 | 读一次记录后报告；不要继续盲等同一任务 |
| `wait-limit` | 本轮等待预算用完，任务仍在运行 | 立刻继续等待同一任务 |

`attention` 提醒有冷却：同一次静默里，第一次到达提醒间隔时报告一次；之后要再经过一个
提醒间隔才会再报一次。真实推进会让计时重新开始。

### 4.1 等待被中断 ≠ 执行被中断

引擎会在**观察者自己的这次请求结束**时报告 `interrupted`（调用方取消、连接断开、引擎在
重建时释放了等待者）。这时任务仍在运行。所以：

- `state` 是 `pending`/`running` 且 `endedAt` 为 `null` 时，这次中断只代表本次观察结束：
  答案立刻返回 `reason: "interrupted"`、`terminal: false`、真实任务状态，指令要求继续等同一
  `taskId`。一次调用**不会**在内部重发观察：被释放的观察者会让每次观察都立刻返回
  `interrupted`，重发就成了请求风暴。
- 只有任务记录本身是 `state: "interrupted"`（重启历史）才是不可恢复的终态：
  `terminal: true`，并且指令明确要求停止盲等、读 `delegate_result`。
- 中断同时带着真实结局时按结局返回：`awaiting-host-review` → `ready`，`failed` → `failed`，
  `cancelled` → `cancelled`，所以已完成的运行照样进审查。
- 状态缺失或未知（本构建不认识的状态字符串）时不做断言：`terminal: false`，指令要求先核对；
  既不宣称"已停止"，也不宣称"仍在运行"。
- `metrics.interruptedObservations` 单独计数，不和心跳混在一起。

任务记录页把真实的 `interrupted` 历史显示为「已中断（进程重启后不会继续执行）」，不会显示
成"仍在运行"。

## 4.2 串行宿主：独立控制通道

插件自己的 stdio MCP 服务器本来就**支持并发**：一个长等待在飞时，status、cancel 照样能被
回答。瓶颈在外层宿主——一次只转发一个工具调用的客户端会让整条连接被等待占住。

插件**不承诺**改变宿主的调度器，也不把长等待退化成轮询。可用的是独立本地控制程序：

```bash
node bin/dsh-delegate-control.js status <taskId>   # 紧凑 JSON 状态（observe + 最小有界观察）
node bin/dsh-delegate-control.js cancel <taskId>   # 只停止这一个任务
```

- 与 MCP 服务器使用**同一个** `createExecutionClient` 与端点发现，调用现有 loopback 执行面；
  不新增权限、开关、配置接口，也没有常驻后台进程。
- 只有这两个动作：没有提交、设置、总开关、批量取消或默认放行。
- `status` 请求的是**最小有界观察**（`waitMs: 1`，引擎与监控都保留的最小正数），不是
  `waitMs: 0`。`0` 在这两处都被理解成"调用方没指定上界"，会被替换成 25 秒的默认长等待，
  反而让一次状态查询超出这条命令自己的预算。它仍然只回答**当前状态**：已结束的任务和待授权
  请求在任何定时器启动前就返回，仍在运行的任务只观察一个切片；永远不读完整结果、diff 或对话。
- **整次命令只有一份总预算**：默认 **10 秒**，`DSH_DELEGATE_CONTROL_TIMEOUT_MS` 只能把它**调小**
  （填更大的值会被夹回 10 秒；缺省或不可用的 `timeoutMs` 也按 10 秒算）。这份预算通过调用方的
  `AbortSignal` 生效，同时**对本次调用禁用观察重试**——否则 1 秒/2 秒/5 秒的退避会超出预算，
  或者在命令已经回答之后还留着请求在跑。没有 `Promise.race`，也不留后台请求或进程。
- 任何断线、超时都变成有界 JSON + 非零退出码（预算耗尽是 `CONTROL_TIMEOUT`），没有堆栈、没有秘密；
  退出码 `0` 有答案、`1` 被拒绝或超时、`2` 用法错误。
- 普通等待**不会周期性跑 status**：这个通道只在操作者或用例显式调用时才发起请求。
- 等待监听断开只释放观察，**取消永远是显式 `cancel`**。
- 工具目录补上了准确的 MCP `annotations`（例如 `readOnlyHint`），便于支持并发的客户端识别
  长等待是只读调用。注解不是修复，串行客户端照样忽略它。

## 5. 等待授权不是卡住

任务等待一次工具调用的授权决定时，仍然是 `running`，阶段是 `awaiting-permission`。
它保留工作区锁和并发名额，并且：

- 这一段等待**不计入**执行超时（有单独的、固定的请求截止时间）；
- 不会被报告成"长时间没进展"；
- 授权决定只对**那一次调用**有效，不构成常规权限，也不会被后续调用复用。

## 6. 集中审查：什么时候读证据

插件不会把对话内容、推理过程或工具输出塞进状态报告。派工方在**执行结束之后**
读一次完整证据（`delegate_result`），然后自己审查：

- 执行完成 ≠ 被接受。插件永远不自行验收；`selfApproved` 恒为 `false`，
  `hostAcceptance` 由宿主自己记录。
- 大改动只挑相关的文件各看一次，不要反复重读同一份证据。

## 7. 续接（跟进任务）

同一个任务的修改、纠正或重试，用 `continueFromTaskId` 提交，并继续使用**同一个**
已授权的源工作区路径。这样跟进任务会续接同一条 DSH 对话、落在同一棵工作树里。
不相关的任务不要复用 id，也不要为了"保持上下文"而续接。

## 8. 已有用户如何升级

1. 在 DSH 的插件设置页打开 **Codex 集成**；
2. 点 **安装 / 更新 Codex 集成**（按钮会把这个插件发布的旧版本文件更新到当前版本）；
3. 让 Codex 重新载入：新开会话或重启 Codex。

`1.2.0` 起，**入口脚本路径未变的已安装托管条目不再需要手工点按钮**：插件启动自检会检查已安装的
`mcp_servers.dsh-delegate` 条目，只要它带托管标记、command 是本包的 Node 命令、`args[0]`
**正好是本安装的** `dsh-delegate-mcp.js`，而且**已经过期**（缺少 `tool_timeout_sec`），就在原地补齐。
入口脚本路径已经指向插件旧目录的条目，启动自检只会报告 `conflict`，不会替操作者改路径：请点
**安装 / 更新 Codex 集成** 或 **修复**，显式动作才会在证明该旧路径是同一包的**真实安装**
（真实目录 + `package.json` 的 `name` 与 `bin["dsh-delegate-mcp"]` 映射都对得上）之后采纳它。

更新会为托管 MCP 条目补上 `tool_timeout_sec = 3660`。客户端可能不认这个字段，或用自己的默认
工具超时提前结束等待（Codex 的历史默认是一分钟）；3660 秒只是把托管条目请求的允许时长设为
默认 3600 秒等待加一分钟余量，**不能**解除客户端自身的限制。这个字段只写在
**本插件自己的** `[mcp_servers.dsh-delegate]` 条目上：

- 旧版本写的、带托管标记的条目会被就地补齐，文件里其它内容原样保留；
- 没有托管标记的同名条目视为**你自己写的**，不会被改写、覆盖或删除；
- 值不是整数的条目同样视为别人的定义；
- 你自己编辑过的子智能体文件会被报告为"不属于已知版本"，插件不会改动它；
- 启动自检**不会创建**条目：没安装就什么都不写；
- `$CODEX_HOME` 或 `agents/` 是链接（含 Windows junction）时一律拒绝，连条目状态都不再
  穿过链接去读；
- 写前重新读取并重新判定，期间发生变化（漂移）就拒绝，不覆盖。

## 9. 已知限制

- 插件的监控只在**有人观察**时运行：没有派工方在等待时，它不启动定时器，也不消耗任何东西。
- 提醒阈值是安全网，不是进度条。插件**不**计算完成百分比，也**不**猜测还剩多久。
- 一次 `delegate_wait` 的默认等待是 3600 秒（上限也是 3600 秒），每次内部观察最多 25 秒；
  前者由工具本身约束，与 `tool_timeout_sec` 的关系是：后者必须比前者略大，才能让一整轮
  等待跑完。
- 等待被中断不等于执行被中断；`interrupted` / `wait-limit` 的 `terminal` 与 `state` 字段是
  判断依据，不要只看原因名字。
- 串行宿主下没有通用的“并发”承诺：插件传输支持并发，独立控制程序只提供 `status` 与
  `cancel` 两个动作，也不能改变宿主的调度方式。
- 设置页的自动刷新只在"任务记录"标签页可见、且存在进行中的任务时运行；
  终端状态的任务不会触发刷新。
